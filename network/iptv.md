# 把运营商 IPTV 接入家庭局域网

家里已有运营商 IPTV 盒子，希望电脑、手机也能看直播。这次在河北移动、中兴 ZXHN G7611V2 光猫和运行 OpenWrt 的小米 CR6608 上完成了接入：路由器独立接收频道组播，通过 udpxy 转成 HTTP，家庭设备用播放器订阅 M3U 列表。

实验发生在 2026 年 11 月 15—16 日，本文整理于 11 月 18 日。家庭网段、设备标识和示例组播地址已泛化；VLAN、接口名和业务行为仍需以各自环境为准。

首次从盒子启动数据中提取到 358 个源，其中 349 个通过路由器校验。这个数量是当时的结果，后续会变化。现已实现已知地址的定时复核和列表发布，运营商新增地址的自动发现、全天节目单的持续获取还没有完成。

## 先把网络和业务分开看

原来的接线是光猫一个口接路由器，另一个口接电视盒子。路由器取得家庭上联网段的地址，盒子取得运营商的另一个私网地址。

这说明需要分别检查上网和 IPTV 的接入，不能因为两个设备都连着光猫，就认为它们在同一个二层网络里。

登录光猫后，重点查看：

- WAN 连接的业务类型、桥接或路由模式。
- 业务 VLAN、公共组播 VLAN。
- LAN 端口绑定、VLAN 绑定方式。
- 各端口的载波、速率、流量和下挂设备。

本次 IPTV 连接名称含 `OTHER_B_VID_301`，实际是桥接业务，业务 VLAN 为 301，公共组播 VLAN 为 302，绑定了光猫 LAN2、LAN3、LAN4。连接名称未必直接写着 IPTV。

**301、302 是本次光猫业务配置中的值，不是频道号，也不代表路由器接入端需要再打同样的标签。** 是否带标签，应结合光猫端口配置和实际报文确认。

最终接线如下：

```text
运营商网络
    │
   光猫
    ├── 千兆1 ── 路由器 wan ── 家庭上网
    ├── 千兆2 ── 原 IPTV 盒子
    └── 千兆4 ── 路由器 lan3 ── IPTV 接收

路由器 br-lan：lan1、lan2、Wi-Fi
路由器 lan3：独立 IPTV 接口
```

WAN 独立，`lan3` 从 `br-lan` 中移除。本机的 `lan1`、`lan2`、`lan3` 显示为挂在底层 `eth0` 上，不能直接把 `eth0` 当作 WAN 或家庭网桥。

机身端口标号也不能替代系统接口名。插拔前后比较载波变化，才能确定实际对应关系：

```sh
ip link show
ip addr show
ip route
uci show network
ubus call network.interface.iptv status
```

光猫端则通过 LAN 状态页确认：新线所在端口为 1000Mbps，盒子所在端口为 100Mbps。速率只是识别线索，仍需结合接线和流量核实。

## 先取得一条真实频道流

普通 DHCP 请求没有收到地址，但不能直接推断成“必须克隆盒子 MAC”或“所有直播都需要盒子鉴权”。换线过程中，旧接口还曾从家庭网络的 DHCP 服务器取得地址；这也不是 IPTV 接入成功的证据，要核对租约来源、网段和路由。

至少要分别验证：

| 层次 | 要确认的事情 |
| --- | --- |
| 物理链路 | 是否有载波、接口是否正确 |
| 地址分配 | DHCP 有没有 Discover、Offer 或 DHCPv6 回复 |
| 组播控制 | 有没有 IGMP 查询、加入和退出 |
| 视频传输 | 是否真正收到 UDP/RTP 数据 |
| 播放解码 | 数据是否能识别为音视频并解码 |

本次先用光猫的**端口镜像**找到频道地址：把盒子所在 LAN2 的报文临时复制到 LAN4，路由器在独立 IPTV 口抓包。这样不用先重启盒子，也能观察它当前正在看的频道。

```text
光猫 LAN2：盒子正常收看
       │
       └── 临时镜像到 LAN4 → 路由器 lan3 → tcpdump
```

观察到的视频结构为：

```text
以太网 → IPv4 → UDP → RTP → MPEG-TS → H.264 / 音频
```

样本中大量 RTP 包是 12 字节头加 1316 字节 TS 数据，1316 正好是 7 个 188 字节 TS 包。这里只是该样本的结构；通用 RTP 解析还要处理 CSRC、扩展头、填充以及 IP 分片，不能始终固定剥掉 12 字节。

另一条同组播地址、不同端口的辅助流也被捕获，但没有进一步确认用途。不要只凭相邻端口就断言它是音频或 FEC。

提取短视频后，用 FFprobe/FFmpeg 识别并解码，确认是 1080p H.264 和音频。直播中途开始抓包时，开头可能暂时缺少 SPS/PPS；应继续观察后续关键帧，而不是只凭第一条解码警告判断流不可用。

镜像只用于发现地址和协议。抓取完成后删除规则，再验证路由器自己的订阅能力。

## 组播转 HTTP：udpxy

播放器请求一个频道时，udpxy 在 IPTV 接口上加入相应组播组，接收节目，再向客户端输出 HTTP 视频流。对于本次 RTP 源，它去掉 RTP 封装，输出 MPEG-TS；不进行视频转码。

```text
手机 / 电脑的 HTTP 请求
    → 路由器 udpxy
    → lan3 上发起 IGMP 订阅
    → 接收 RTP / MPEG-TS
    → HTTP 返回给播放器
```

本次的重要发现是：虽然没有拿到 IPTV DHCP 地址，给 `lan3` 配置本地地址 `169.254.77.1/32` 后，已能完成组播订阅和接收。随后盒子切换到另一个频道，电脑端原频道仍能继续播放；关闭镜像后，两个不同频道的 HTTP 并发接收也通过了测试。

这只证明了本次环境下已测试频道的接收方式，不保证其他地区、付费频道或加密业务也成立。盒子关机后的情况没有专门验证。

下面是本次 IPTV 接口的配置片段，应合并进已有配置，不能覆盖整份网络配置；同时先把 `lan3` 从原家庭网桥的端口列表移除。

```text
config interface 'iptv'
    option device 'lan3'
    option proto 'static'
    option ipaddr '169.254.77.1'
    option netmask '255.255.255.255'
    option defaultroute '0'
    option peerdns '0'
    option delegate '0'
    option ipv6 '0'
```

这个本地地址不是运营商分配的地址，也没有给路由器建立访问运营商单播业务的完整路径。它能接收组播，不代表能访问节目单服务器。

防火墙使用独立 `iptv` 区域：一般入站和转发拒绝，出站允许；另外允许该区域的 IPv4 组播 UDP（目的 `224.0.0.0/4`）和 IGMP 入站。家庭设备经 HTTP 访问路由器，不需要进入 IPTV 专网。

udpxy 配置示例，家庭网段使用泛化后的 `192.168.50.0/24`：

```text
config udpxy
    option disabled '0'
    option respawn '1'
    option status '1'
    option bind '192.168.50.1'
    option port '4022'
    option source 'lan3'
    option max_clients '8'
    option buffer_size '262144'
    option mcsub_renew '30'
```

```sh
/etc/init.d/udpxy enable
/etc/init.d/udpxy restart
```

播放器中的示例地址：

```text
http://192.168.50.1:4022/rtp/239.1.1.1:8000
```

这里的组播地址和端口只是示例。实际值应来自抓包；不同频道的端口不一定相同。路径中的 `rtp` 对应本次源的封装，原生 UDP/TS 源需要另行确认。

HTTP 200 也不足以证明播放成功：代理可能已经返回响应头，却没有收到节目数据。要继续检查字节流和解码结果。

## 从盒子启动过程取得频道表

换台时观察 IGMP 和视频流可以逐个收集地址，但更高效的方式是抓盒子加载频道表的过程。

第一次退出直播、重新进入直播并翻动频道列表时，捕获到：

```text
POST /VSP/V3/QueryChannelListBySubject
```

该分类目录一次返回 270 项，包含名称、频道号、频道 ID 和媒体 ID，**没有直接给出组播地址**。媒体 ID 不能拿来猜组播 IP 或端口。

后来在抓包就绪后重启盒子，捕获到：

```text
POST /EPG/jsp/getchannellistHWCTC.jsp
```

响应中的脚本通过盒子原生接口写入频道表，形如下面的示意片段：

```javascript
Authentication.CTCSetConfig(
  'Channel',
  'ChannelID="10001",ChannelName="示例频道",UserChannelID="1",ChannelURL="igmp://239.1.1.1:8000"'
);
```

这次初始化表有 358 项，并提供了真实端点。270 与 358 是不同阶段、不同口径的目录，不能把前一次分类查询的数量当作全部源数。

需要保留的字段是频道 ID、名称、频道号、组播地址和端口。响应中还可能混有会话、时移和鉴权 URL，应在导出时按字段筛选，原始抓包单独保管，不跟分享笔记或公开列表一起发布。

### 抓包过滤踩过的坑

第一轮想排除组播视频，只抓“非组播 UDP”，结果漏掉了 **IPv6 单播视频**。视频流迅速占满环形文件，覆盖了进入直播时的早期控制请求，不得不重新操作一次。

第二轮收紧到盒子 MAC 对应的控制协议，才完整保留请求。下面的 MAC 是本地管理地址示例，使用前替换为自己设备的值：

```sh
tcpdump -ni lan3 -s 0 -U -C 12 -W 4 \
  -w /tmp/iptv-control.pcap \
  'ether host 02:00:00:00:00:01 and
   (tcp or igmp or arp or icmp6 or
    udp port 53 or udp port 67 or udp port 68 or
    udp port 546 or udp port 547 or udp port 9875)'
```

这是一份针对本次业务的过滤条件，不是万能 IPTV 过滤器：视频也可能走 TCP，控制协议也可能使用其他端口。

还要注意：

- 过滤盒子 MAC 会漏掉目的为其他组播 MAC 的广播类报文，例如发往全节点的 IPv6 RA。排查地址分配时应单独抓相应协议。
- `-C 12 -W 4` 把环形文件限制在约 48MB，但容量不足仍会覆盖最关键的启动数据；应该及时复制、分析和停止。
- 长 HTTP 响应可能跨多个 TCP 包，需要按连接和序号重组，再处理 Content-Length、chunked 和压缩；不能只对单个包搜索关键字。
- 临时镜像与抓包完成后要清理。正常播放应在关闭镜像的情况下重新验证。

## 让播放列表能长期维护

M3U 只是名称到播放地址的映射。示例：

```text
#EXTM3U
#EXTINF:-1 tvg-id="10001" group-title="示例",示例频道
http://192.168.50.1:4022/rtp/239.1.1.1:8000
```

自动化分为两个不同任务：

1. **发现和更新源地址**：从运营商目录取得新增或迁移后的端点。
2. **复核和发布已有地址**：检查已知源，生成当前可用的列表。

本次完成的是第二项。第一项目前仍依赖启动抓包导入，不能把“脚本每天运行”称为已经完成源地址的自动发现。

校验和发布流程：

```text
已知源表 → 取得短样本 → 检查 TS → 合并历史状态 → 原子发布 M3U / 状态 JSON
```

每频道最多取 256KiB、等待最多 8 秒，检查 HTTP 状态、最小数据量、188 字节间隔的 TS 同步字节，以及样本前 80 个包的加扰标记。这是传输格式检查，完整音视频解码和长期稳定性仍需额外验证。

首次复核 358 个源时，349 项通过，9 项无流或带加扰标记。随后使用以下策略减少短暂网络波动的影响：

- 同一已发布地址连续两次失败后移出，恢复后自动加入。
- 修改后的新地址必须重新通过检查，不能继承旧地址的成功状态。
- 所有源都失败时保留上一版，状态明确标记为保留旧版，不发布空列表。
- 使用运行锁防止重叠任务，使用目标目录中的临时文件加 `rename` 原子替换。

因此“已发布”和“本次检查通过”可能不同，界面应分别显示。一次失败、全失败保留旧版时，列表里仍可能存在暂时不可用的条目。

定时任务每 6 小时运行一次：

```cron
17 0,6,12,18 * * * /root/iptv/bin/iptv-update >> /root/iptv/log/update.log 2>&1
```

状态页面做成单个 HTML，使用 Preact + htm ESM，不引入构建流程。它读取同目录的 `iptv-status.json`，支持搜索、分组、异常筛选、复制地址和导出筛选内可用频道。页面每 60 秒读取状态，刷新按钮只读最新结果，不触发整个源表的重新检测。

本次使用的公共库：

- React/Preact/htm 入口：<https://lsong.org/scripts/react/index.js>
- 公共样式：<https://lsong.org/stylesheets/index.css>

## 配置集中管理与版本控制

把实际文件集中到 `/root/iptv/`，系统原路径通过软链接引用：

```text
/root/iptv/
├── bin/         校验脚本、入口恢复工具
├── config/      源表、network、firewall、udpxy、crontab
├── init.d/      udpxy 服务脚本
├── index.html   状态页面
├── var/         持久运行状态，不进 Git
├── www/         生成的 M3U / JSON，不进 Git
├── log/         指向 /tmp 日志的链接，不进 Git
└── backups/     配置备份，不进 Git
```

主要引用关系：

| 系统入口 | 实际文件 |
| --- | --- |
| `/usr/bin/iptv-update` | `/root/iptv/bin/iptv-update` |
| `/etc/config/udpxy` | `/root/iptv/config/udpxy` |
| `/etc/crontabs/root` | `/root/iptv/config/crontab` |
| `/www/iptv.html` | `/root/iptv/index.html` |
| `/www/iptv.m3u` | `/root/iptv/www/iptv.m3u` |
| `/www/iptv-status.json` | `/root/iptv/www/iptv-status.json` |

这次也把 network、firewall 集中到 config；它们仍是整机共享配置，包含家庭网络和其他业务，不能只按 IPTV 配置理解或回滚。

软链接迁移前，先用独立临时配置验证本机 UCI 提交是否保留链接；迁移后用真实分钟任务验证 cron 是否能读取软链接文件，而不只检查“进程正在运行”。

发布脚本必须向实际 `www/` 目录写入并原子替换。如果把临时文件直接 `rename` 到 `/www/iptv.m3u`，可能替换掉入口软链接本身。

Git 只追踪脚本、配置和文档。状态、样本、生成列表、日志及备份忽略；升级保留清单中加入 `/root/iptv/`，同时确认新固件仍有运行所需的软件包。

还有两处环境经验：

- 本次固件使用 `apk`。包管理器、可用命令和参数应以设备实际输出为准，BusyBox 工具通常不能直接照搬桌面命令参数。
- 路由器上的 `jq test()` 实测触发异常退出，而普通 JSON 操作可用。校验改用不依赖正则函数的写法，并在真实设备上复测；电脑上测试通过不等于路由器上也能运行。

## 节目单是另一条链路

直播地址和节目单不是同一份数据。盒子通过 IPv6 请求：

```text
POST /VSP/V3/QueryPlaybillContext
```

请求会指定频道、时间以及前后节目数量；响应中有 `channelDetail`、`prePlaybillLites`、`currentPlaybillLite`、`nextPlaybillLites`，节目字段包含名称、频道 ID、开始和结束时间。抓到的时间值是 Unix 毫秒，转换时要区分秒、毫秒和时区。

已有抓包提取出 28 个频道、89 条去重节目，但只是历史部分快照，既不是当前节目单，也不是全部频道的全天节目单。以后输出 XMLTV 时，应与 M3U 的 `tvg-id` 使用同一套频道 ID。

主动访问运营商接口仍未成功：

- IPTV 口临时开启 IPv6 并尝试 DHCPv6，没有拿到地址。
- 使用抓包中的 `hbtv` 业务标识、请求选项等继续测试，没有收到预期回应。
- 仅发送 DHCPv6 SOLICIT 的诊断也没有获得回应，没有进入正式地址申请或应用候选地址。
- 从普通 WAN 路径请求 EPG 服务器连接超时；复用抓到的会话也未打通主动查询。
- 盒子没有可用的 ADB/网络调试入口。

这些结果仍不足以区分光猫端口策略、设备注册、接入数量限制和其他网络条件，不能直接下结论说一定是 MAC 绑定或 Cookie 失效。所有失败试验的临时网络、防火墙设置都已撤回。

下一步原计划在方便停电视时，把路由器的 IPTV 上联临时从光猫千兆4移到千兆2，先测试路由器自身能否得到回应，以区分端口和设备因素。这个接线测试尚未执行。

**能接收直播组播，不等于已经获得节目单服务器的单播路径和有效会话。** 本次选择继续使用运营商自己的节目单，没有用其他来源填补为“已完成”。

## 浏览器辅助检查的经验

登录光猫后的页面可以通过 Chrome CDP 只读检查，但实际要看当前浏览器和工具的支持情况。

本次开启现有 Chrome 的远程调试后，`/json/version`、`/json/list` 返回 404，仍可通过用户目录中的 `DevToolsActivePort` 找到浏览器 WebSocket 路径并连接。不能仅凭这两个 HTTP 端点的状态判断 CDP 是否启动。

光猫页面使用 frame，顶层 `document.body.innerText` 基本为空，实际内容位于 `mainFrame`。检查时先看页面结构，再定位内容：

```javascript
frames['mainFrame'].document.body.innerText
```

这属于本次浏览器和光猫实现的观察，不保证其他版本仍采用同样结构。浏览器调试连接也不能代替对网络访问权限和执行环境的确认。

## 日后重新排查时的顺序

1. 记录接线、接口载波、路由和备份，明确要保留的业务。
2. 检查光猫业务连接与端口绑定，隔离 IPTV 口。
3. 找到一个真实端点，验证数据接收和解码。
4. 关闭镜像，再测试独立订阅、盒子换台和并发播放。
5. 抓启动初始化表，批量取得地址，去重并逐项复核。
6. 给列表发布加状态、失败策略、锁和原子替换，再启用定时任务。
7. 将直播、目录更新、EPG 获取分别列出完成情况和待验证条件。
8. 保存可复现的配置与结论，清理镜像、抓包进程和试验规则。

最值得保留的经验是：**每一层都要有自己的证据。看到端口亮、DHCP 失败、HTTP 200 或频道目录，都不能直接跳到“可播放”或“已经自动更新”的结论。**
